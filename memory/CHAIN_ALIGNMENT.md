## §3 · The journey of one job

**On the phone (JS)**

1. Create the job: ship, date, name (action chips + equipment; optional ✨ Thai → the archive's English).
   **Every job gets a new `job_id`, and none is ever reused.** Next month's routine on the same machine is a
   new job with its own date. It is never an edit or a resend of last month's job (Nick, 2026-10-30, EMR
   `ff79d2d`). Measured on 2026-10-30, reading the code, why it must stay so:
   - HPO files by `job_name` + `work_date`, not by `job_id` (`find_filed_job`). A reused id with a new date
     would still get a new folder.
   - But the phone asks `GET /jobshot/v1/job/<id>` before it sends (step 15; JS `statusOf`). It would find
     last month's filing, mark the new job filed and **never send it**, with no error anywhere.
   - JS mints a new id for every job today, *Do it now* included (`JobStore.createJob`).
   **Agreed by all three, 2026-10-30 — a QR scan starts a routine's next round** (Nick's direction and his two
   answers; JS `eb1eb30`; EMR `c9e2c55`, `40c0792`). **Nick accepted it as JS ADR-0008 (2026-10-30, JS
   `8fc082d`). It is built in stages, each behind its own gate; only stage 0 is built:** a JS test pins the
   words the phone writes to {typed, ai_confirmed} (`test/provenance_test.dart`).
   - New job offers a QR scan. Scanning a machine's label starts a **new job**: it never copies the old date
     or `job_id`. HPO files it under its own date like any other job, and nothing is asked of HPO.
   - **The scan is a prefill, not a lock.** Everything stays editable before Create, because a breakdown on a
     routine machine is scanned the same way.
   - **What the scan carries** (Nick chose JS's list):
     - prefilled: `equipment_id`, Equipment, Model, Serial and the job name;
     - offered as "Last time (date)" and taken with one Accept: the type, the Action and Test text, and
       spare rows without their serial;
     - never carried: Problem, Cause, Pass/Fail, a spare's serial, photos and tags, the date and the id.
   - **The round counts at the job's first photo** (Nick chose it over counting at the scan; the BUG-013
     lesson). JobShot updates its routine itself. A routine learns its `equipment_id` on the phone only,
     and a scan never creates a routine.
   - **The source is EMR's live lookup** (`/emr/v1/thing`), because it alone has the report as filed,
     PC-side changes included. One limit: an edit made later in Word, to the `.docx`, is not in it. With
     the PC off, the register copy gives the machine's facts only. The phone's own old draft is never used.
   - **`scanned`** = copied from EMR because of a scan, accepted on the scan sheet, and unchanged since.
     Any edit makes it `typed`. It covers sections and spare fields only; equipment fields carry no
     provenance. EMR prints it like `typed`, unlike `ai`. Because it prints, a routine job carrying last
     month's accepted text plus one tagged photo is written automatically, with nobody reading it at the PC.
   - **Order:**
     1. a CHAIN_CHECKLIST line with the EMR version;
     2. EMR ships `scanned` in TRUSTED_SOURCES, with a test pinning exactly {typed, ai_confirmed, scanned};
     3. that EMR is installed on the ship's PC;
     4. only then does JS list it.
     Measured why: EMR up to v0.5.1 (v0.5.2 did not change `TRUSTED_SOURCES`) drops a `scanned` section and blanks a `scanned` spare field, and the
     automatic road holds the job as "need you".
   - **Still before stages 1-3** (ADR-0008 §Stages; Nick's go passes no gate):
     - stage 1 (EMR pairing, hello, register copy): the EMR-LAN-test, which chooses the label address,
       and the lookup endpoint (EMR step 4), with a firewall/admin check on a ship PC;
     - stage 2 (scan on New job, count at the first photo): stage 1, and a CHAIN_CHECKLIST line for
       `equipment_id`;
     - stage 3 (the "Last time" offer as `scanned`): the order above. Until then the phone shows no
       "Last time" offer at all.
2. Photograph, and **tag each photo Before / After / part-label.** The phone cannot infer this.
3. Optionally fill the report page: equipment / model / serial, preventive|breakdown, pass|fail, the
   four sections, spare parts.
4. **Provenance is set here.** An AI-suggested value enters a box only when the engineer taps it, and
   the tap marks it `ai_confirmed`; a typed value is `typed`. **The phone never writes a bare `ai`.**
5. `finalise()` writes in this order and no other: renumber photos → `emr.json` → **`job.json` LAST.**
   `job.json` is the completion marker; HPO keys on it.
6. One tap sends the job to the paired PC over the LAN. (Zip via share / save dialog is the fallback.)
7. The receipt naming the filed folder is **the only thing that makes deleting the job from the phone safe.**

**On the PC (HPO) — no human step in this segment**

8. The receiver runs while the app is open; the phone is paired once per PC by QR (host · port · vessel · token).
9. Gate the zip: images and JSON only; `"jobshot"` must be the integer `1`; `job_name` non-empty;
   `photos[]` non-empty.
10. A job from the phone **skips the AI naming and the review entirely** — it arrives already named and grouped.
11. Resize into the 10–25 KB band, name the folder `DD-MM-YY <Job name>`, rename every photo after its folder.
12. **Choose the day number — see §5.**
13. Write HPO's own `filed` block into the archived `job.json`: `folder`, `folder_date`, `work_date`,
    `date_shifted`, `merged_into_existing_folder`, `grouped_with`, `extras`, **`renamed`**, `hpo_version`,
    `filed_at`.
14. Copy `emr.json` **byte-for-byte and never parse it.** Carry any other `*.json` sidecar the same way
    (a name matching `job.json` / `job-*.json` is read as a manifest, not carried).
15. Answer the receipt, and record it in `jobshot_filed.json` so `GET /jobshot/v1/job/<id>` can answer a
    lost reply. Its 404 carries `unreadable_records` when a `job*.json` cannot be parsed (HPO `630e674`+), so
    "not filed" is never claimed from a damaged record.

**On the PC (EMR)**

16. Open the month folder, click the job; the form fills.
17. Read `emr.json` — gate `"emr": 1`; **every other field optional**; an unrecognised shape is dropped
    **per field**, never wholesale, and **the reader never raises.**
18. Read `job.json` for exactly three keys: `filed.extras`, **`filed.renamed`**, `filed.folder`.
    **No content ever comes from `job.json`.**
19. **Drop any value not marked `typed` or `ai_confirmed`.** Refuse with a stated reason in three cases:
    two manifests naming one draft, `filed` without `renamed`, photo names resolving to nothing.
20. The engineer presses **Create report.** The `.docx` is written beside the photos, and the folder then
    remembers the job is done (a `.docx` present = done).
21. **EMR v0.4.9+ also writes `report_history.json` beside the `.docx`** (Nick, 2026-10-29: the ship's
    history must outlive one PC). On every scan EMR files copies its PC lacks, so a new or second PC gets
    the history back by opening the archive. Making the report again overwrites it; EMR writes no other
    file in the folder.

## §5 · THE DATE RULE — Nick's ruling, binding on all three

> **HPO looks in its own destination folder, on the real machine's path, for a day number in that
> month that is not yet used. Every free day is filled before any day number repeats. Once the month
> has no free day left, repeating a day number is allowed.**

1. **`work_date` from the phone is an input, not the answer.** HPO may move the folder to a free day;
   when it does, `filed.date_shifted` is `true` and `filed.work_date` still records what the phone said.
2. **Unique while any day is free. Duplicates only when the month is full.**
3. **EMR prints the folder's date.** Duplicate day numbers are safe there — jobs are keyed by *path*,
   `is_done` asks only whether a `.docx` sits in that folder, and the list sorts by `(date, name)`.
4. **A folder name must never carry a date range.** `assign_unique_dates` can hand a day inside the
   range to another folder in the same pass, so reader and writer would disagree within one run.
5. **The mechanism, stated so nobody re-derives it wrongly:** HPO's used-day scan reads **the folders
   present on disk**, not `jobshot_filed.json`. **Deleting a folder returns its day to the pool**, and a
   later job may legitimately take that day again. The duplicate day numbers observed on 2026-09-26
   (day 26 ×2, day 01 ×2 in one destination, while 4 of the 5 filed folders had been removed) are almost
   certainly this and not a defect — **HPO: confirm against your own `scan_used_days()` and say so.**
6. ⛔ **How to test this rule — Nick cannot create 30 jobs.** Do **not** test by deleting folders and
   watching what happens; that exercises the pool-release path, not the full-month path. **Create empty
   placeholder folders to fill every day of a test month, then file one more job and record what it does.**
   All three projects must be able to state the same expected outcome before the test runs.

### §6.4 · Two silent-loss paths found on 2026-09-26 in the real run — added after issue

**§6.4a — `spares` and `spare_parts` are both accepted, and sending both loses everything.** EMR
resolves them as `raw.get("spares", raw.get("spare_parts"))`, so the fallback runs **only when
`spares` is absent**. A writer that emits `"spares": null` **alongside** a populated
`"spare_parts"` loses every row **silently, with `dropped: 0`** — nothing was refused, because
nothing was offered. **JS sends exactly one of the two keys.** EMR has specified it and pinned it
with a test rather than guessing which key a writer meant. Full field-by-field spec:
`Engine-Maintenance-Report/docs/SPARE_PARTS_SPEC.md`.

**§6.4b — the ship name on the controlled document can differ from the job's, silently.** By EMR's
contract §0 the Ship Name comes from **EMR Settings** and never from the phone. Measured on the
21:27 job: `emr.json` says `ship: ENA Test`, and the issued `.docx` prints **`ENA Challenger`**.
Working exactly as specified, and harmless tonight because both are test values — **but this is a
controlled document that names a vessel.** Not fixed unilaterally by anyone: **if the phone's
`ship` is ever to be authoritative, that is a contract decision and it is Nick's.** Until then all
three know the two can disagree, and EMR is not at fault for the divergence.

## §8 · How a version reaches each app — measured, not assumed

| | Route | What that costs |
|---|---|---|
| **JS (phone)** | **There is no in-app updater.** `AppVersion.isNewer()` exists and **only tests call it.** Every version reaches the phone by someone building the APK and installing it over USB. | ⚠️ The phone cannot be updated, and its version cannot be verified, unless it is plugged in. The APK is **debug-key signed**; moving to a real keystore **requires an uninstall, which deletes the jobs on the phone.** A split-per-abi APK and a fat APK **cannot be installed over each other** (`versionCode` 2000+N vs N). |
| **HPO** | In-app updater, GitHub release, SHA-256 from the release notes. | The update cache reclaims itself after an install (measured 2026-09-26: 87.4 MB → 0). |
| **EMR** | In-app updater, `nicksuksantr-pixel/EMR-releases`, SHA-256 from the release notes, swap-by-rename on exit. | **It re-downloads the full 41.7 MB even when a verified zip is already staged** — `download()` has no already-have check, and a tie goes to the internet because the folder road carries no checksum. Deliberate, and written here so it is not discovered on a ship's link. |
